# CHANGELOG

## `v6.0.0` (unreleased) — Cleanup means cleanup

The first major since `v5.1.0`, and the combined result of four consecutive audits of the whole library — dispatch, retain semantics, listener lifecycle, types, build configuration, and docs. **It is not published.** `package.json` carries `6.0.0-dev`, and `scripts/publishPackage.cjs` refuses to publish any version ending in `-dev`, so `npm view @spearwolf/eventize dist-tags` goes on answering `latest: 5.1.0` until this section gets a version without the suffix and a date. Everything below is stated against `v5.1.0` — the version consumers actually have. The staging versions this work passed through reached nobody and are not history worth carrying: a `v5.1.0` consumer takes one jump, and takes all of it at once.

Thirteen breaking changes. The two with the widest blast radius are every bulk `off()` form — `off(ε)`, `off(ε, '*')`, and any array containing `'*'`, `null` or `undefined` — now clearing retained state along with listeners, where it used to leave the keeper untouched, and `once()` no longer deduplicating, so two `once()` calls on the same listener object mean two independent one-shot firings instead of one listener that used to collapse into a permanent subscription. Two further changes alter runtime behavior without being breaking by the letter — an event name colliding with an inherited `Object.prototype` member no longer dispatches to it, and `off(ε, '*', listenerObject)` stopped being a silent no-op — and a `v5.1.0` consumer meets both in the same install. See [`docs/lifecycle.md#migrating-from-v5`](./docs/lifecycle.md#migrating-from-v5) for before/after snippets and [`skills/using-eventize/references/migration.md`](./skills/using-eventize/references/migration.md) for the full list; reach for `getRetainedCount(ε)` / `getSubscriptionCount(ε)` to confirm a migration actually worked. Test suite at 683 cases across 29 spec files, up from 25 files in `v5.1.0`.

- **BREAKING:** `once()` no longer deduplicates against existing listeners. Two `once(ε, 'foo', listenerObject)` calls on the same object used to collapse into one `EventListener` with `refCount = 2`; both set `callAfterApply` in turn, the second overwrote the first, and after the first emit only one `unsubscribe` ran — dropping the count to 1 while its own idempotence guard stopped the surviving handle from ever decrementing again. The result fired on every subsequent emit and could only be removed by an external `off(ε, listenerObject)`. Each `once()` now gets its own listener instance, so two one-shot subscriptions mean two firings and each returned handle releases exactly its own. A retained event is replayed to each of them, because every registration is now a genuine insert. **Migration:** code that registered the same listener object with `once()` more than once and expected a single call now receives one call per registration. `on()` is unchanged — reference-counted dedup there is documented and intended. Affects `src/EventStore.ts`, `src/subscribeTo.ts`, `src/eventize-api.ts`.
- **BREAKING:** Every bulk `off()` form — `off(ε)`, `off(ε, '*')` and an array containing the wildcard, `off(ε, ['*', …])` — now clears retained state as well as listeners. Previously they emptied the listener registry completely and left the `EventKeeper` untouched, so retained payloads stayed strongly referenced and were still replayed to any subscriber arriving afterwards — the call everyone reads as "everything gone" was precisely the one that cleared nothing, while `off(ε, eventName)` had always dropped both the value and the policy for its name. The array form was the worst of the three: `off(ε, ['*', 'foo'])` removed every listener but dropped only `'foo'`'s retained state, leaving every *other* retained name pinned and still replaying — a partial wipe that looked targeted and behaved like neither. The keeper now uses the same `hasWildcard()` test that `unretain()` and `retainClear()` already apply, so a wildcard anywhere in the array means "everything", matching what `EventStore.remove()` has always done to the listeners. **Migration:** code that relied on retained values surviving a bulk `off(ε)` must re-`retain()` and re-`emit()` afterwards, or switch to the targeted `off(ε, eventName)` / `off(ε, [names])` forms, which are unchanged as long as no `'*'` appears in the array. `getRetainedCount(ε)` makes the difference visible in a test. Affects `src/eventize-api.ts`.
- **BREAKING:** An `off()` array holding a `null` or `undefined` element now clears retained state, the way an array holding `'*'` does. `EventStore.remove()` tests `Array.isArray` *before* its wipe branch and forwards every element back into itself with a null listener object, so one nullish element lands in that branch and empties the whole registry — `off(ε, [null])` and `off(ε, ['foo', null])` have always removed every listener. The keeper's guard tested only for the wildcard, so `off(ε, [null])` left every retained value and policy in place while the store was empty, and `off(ε, ['foo', null])` dropped exactly one name's retained state out of a total wipe — the same "partial wipe that looks targeted" shape as `off(ε, ['*', 'foo'])` above. In `v5.1.0` no bulk form touched the keeper at all, so the two agreed by doing nothing; `off(ε)` and `off(ε, '*')` clearing it is what would have made the sibling form incoherent. The keeper guard now mirrors the store's *effective* behaviour rather than its condition. **Migration:** the same as for the other bulk forms — re-`retain()` and re-`emit()`, or keep nullish values out of the array, which is worth doing anyway: an event-name list built at runtime wipes the emitter as soon as one lookup misses. Affects `src/eventize-api.ts`. Three cases in `src/off.spec.ts`.
- **BREAKING:** A method-name subscription whose listener object is missing — `on(ε, 'foo', 'handler', null)`, or the same call with the fourth argument left off — now dispatches to nothing instead of throwing `TypeError: Cannot read properties of null`. `null` is an accepted value of `ListenerObjectType`, so the crash was never a documented contract, and the surrounding branch already tolerates a listener object that has no such method yet (the `once()` fix below). A `once()` in this shape is not consumed, matching the late-bound listener object it now behaves like. Reading the method off a **function** used as the listener object — `on(ε, 'foo', 'reset', SomeClass)` — keeps working. Affects `src/EventListener.ts`; three cases in `src/EventListener.spec.ts`.
- **BREAKING:** The `unsubscribe` handle returned by `on()` is single-shot. Calling it a second time is now inert; it used to run a second `off()`. `on()` collapses an identical listener-object subscription into one `EventListener` with a reference count, so two handles shared one registration and one handle called twice decremented it twice — destroying the *other* handle's subscription. `const u1 = on(ε, 'foo', lo); on(ε, 'foo', lo); u1(); u1();` left `getSubscriptionCount(ε) === 0` where it should have left 1. `docs/off.md` has promised "calling it more than once is safe — subsequent calls are no-ops" the whole time, and defensive cleanup code that calls a stored handle unconditionally is exactly the shape that hit it. `once()` already carried this guard in `v5.1.0`; it now lives in `makeUnsubscribe()`, which both share, so `once()`'s own wrapper is gone. **Migration:** code that unsubscribed, re-subscribed through a *new* `on()` call, and then reused the *old* handle to unsubscribe again now finds the old handle inert — keep the handle the second `on()` returned. Affects `src/eventize-api.ts`. Two cases in `src/off.spec.ts`.
- **BREAKING:** `on()` and `once()` reject a listener they could never dispatch to, instead of registering it. `_subscribeTo()` tested truthiness and nothing else, so `on(ε, 'foo', 5)` built an `EventListener` whose `listenerType` was `undefined`, `getSubscriptionCount(ε)` reported it, and every `emit(ε, 'foo')` fell through all three branches of `EventListener.apply()` and returned — a subscription that existed for counting and cleanup purposes but never called anything, removable only with an explicit `off()`. The same call with `0` in the listener slot threw, because `0` is falsy: a numeric value forwarded into that position behaved in opposite ways depending on its value, and the silent half was the one that looked like it had worked. The filter is now `detectListenerType()` — the same function `EventStore.isSimilar()` tags listeners with — so only a function, a string, a symbol or a non-null object gets through, and the falsy test stays in front of it so an empty method name (`''`, which does carry a tag) keeps being rejected as before. This is what makes the `undefined` branch in `apply()` unreachable through the public API rather than merely claiming to be. The thrown message is unchanged (`subscribeTo() called with insufficient arguments`); the accompanying `console.warn` now distinguishes a missing argument from an unusable one. **Migration:** a call site that passed a number, a boolean, a bigint or any other non-dispatchable value as the listener now throws where it previously registered a dead entry — most likely a forwarded config value or an argument in the wrong position, which is precisely what the change is meant to surface. Nothing that ever dispatched changes: every documented spelling of `on()` — listener function, method name plus listener object, listener object alone, catch-all, arrays and `[name, priority]` tuples — is unaffected and pinned by spec. Affects `src/subscribeTo.ts`, `src/EventListener.ts` (`detectListenerType()` is now exported internally). Eight cases in `src/on.spec.ts`; in `src/EventListener.spec.ts` one existing case rewritten — the primitive listener it asserts about has to be added to the store by hand now that `on()` refuses to build it — plus two new ones beside it, a control proving that same hand-registered path does collect from a real listener, and one pinning that `on(ε, 'toFixed', 42)` throws and leaves the subscription count at 0.
- **BREAKING:** A `NaN` priority now throws instead of quietly misplacing the listener. `NaN` is a `number`, so it passed the positional decoding as a valid priority — and then poisoned the ordering: `sortByPriorityAndId()` compares with `b.priority - a.priority`, which is `NaN` for every pair, every comparison is false, `findInsertIndex()` runs its binary search all the way right, and the listener ends up at a position determined by the size of the bucket rather than by any priority relation. `on(ε,'foo',10,…)`, `on(ε,'foo',NaN,…)`, `on(ε,'foo',5,…)` dispatched as ten, nan, five, with no error and no warning. The realistic way in is arithmetic on unvalidated input — `on(ε, 'foo', Number(cfg.prio), fn)` with an unparsable `cfg.prio` — which is why the code already went out of its way to keep `undefined` out of the same arithmetic for priority-less tuples. The check is `Number.isNaN`, deliberately **not** `Number.isFinite`: `Priority.Max` and `Priority.Min` are `±Infinity`, they sort perfectly well, and they stay valid — as do `0` / `Priority.Normal` and every other finite value. It covers all four positions a priority can occupy: `on(ε, prio, fn)`, `on(ε, name, prio, fn)`, the `[name, priority]` tuple form, and the same shapes through `once()`. The tuple form rejects **atomically** — a `NaN` anywhere in `on(ε, ['a', ['b', NaN], 'c'], fn)` registers nothing at all, matching how `retain(ε, [name, …])` handles a wildcard rather than how `emit()` does. One case rejects a `NaN` that would never have reached a comparison: `on(ε, [['a', 5], ['b', 7]], NaN, fn)` used to subscribe both names at their tuple priorities, the call-level `NaN` overridden everywhere and harmless. It now throws, because the call-level priority is validated before the array branch resolves the overrides. That is deliberate — the number is broken at the call site whether or not this particular argument list happens to bury it, and a check that passed depending on how many tuples carried their own priority would be worse than either answer. The message is `subscribeTo() called with a NaN priority`. **Migration:** validate the number before it reaches `on()` — `Number.isNaN(prio) ? Priority.Normal : prio` restores the old *intent* (a listener at default priority) far better than the old behaviour did, which was an unspecified position. Affects `src/subscribeTo.ts`. Nine cases in `src/on.spec.ts`, three of them pinning `Priority.Max`, `Priority.Min` and the priority-less tuple as still valid.
- **BREAKING:** `off(ε, <numeric listener id>)` no longer removes anything. `EventListener.isEqual()` matched a number against its own `id`, and `v5.1.0`'s handle exposed the instance as `unsub.listener`, so `off(ε, unsub.listener.id)` worked — undocumented, untested, and reachable only by reading the instance the handle carried. It also disagreed with every documented removal path: `unsub()` goes through `removeByEventListener()` and decrements the reference count, while the id match detached the listener outright, taking a subscription two handles shared down to zero at the first call. Documenting it would have meant documenting an alias for `unsub()` that behaves differently from `unsub()`. The number is now an ordinary unrecognized listener, i.e. a silent no-op — and with the handle reduced to `() => void` (below) there is no supported way to obtain such an id at all. Affects `src/EventListener.ts`. One case in `src/off.spec.ts`.
- **BREAKING:** An `EventListener` constructed with a `null` or `undefined` listener now has `listenerType === undefined` and dispatches to nothing, instead of being tagged `LISTENER_IS_OBJ` — `typeof null === 'object'`, and `apply()` then dereferenced the null. Two consequences: such a listener no longer throws a `TypeError` when an event reaches it, and two of them are no longer treated as similar, so they no longer collapse into one reference-counted entry in the store. Unreachable through the public API — `on()` / `once()` reject a falsy listener with a thrown error before an `EventListener` is ever built — so this only affects code constructing `EventListener` directly, which this release makes impossible from outside the package: the class is no longer exported in either namespace.
- **BREAKING (types):** `UnsubscribeFunc` is now `() => void`, and `EventListener` is gone from the published surface entirely. The handle returned by `on()` and `once()` no longer carries `.listener` (single-name forms) or `.listeners` (array form). In `v5.1.0` the declared type was a union of `(() => void) & {listener: EventListener}` and `(() => void) & {listeners: EventListener[]}`, and TypeScript can never tell two arms of a union apart, so *both* fields were a `TS2339` at every call site — including in the published `lib/index.d.ts`. `off(ε, unsub.listener)`, the cleanup form `docs/lifecycle.md`, `docs/off.md` and `references/migration.md` all described, did not compile against the declarations that shipped; and the `EventListener` those fields named was not even this package's class, because `src/types.ts` used the name without importing it and it silently bound to the **DOM** global `(evt: Event) => void`. The properties also handed out an internal class no consumer could construct, subclass or `instanceof`, because the runtime bundles never exported it. The audit's own recommendation — split the return type per overload arm so both fields become readable — was rejected: it would have legalised traversing into the `EventListener` for the first time and made an internal shape supported API. **Migration:** replace `off(ε, unsub.listener)` with `unsub()`. Both go through the same reference-counted removal path, both are single-shot, and `unsub()` does not need the emitter in scope. Reads that went further in — `unsub.listener.id`, `.isRemoved`, `.callAfterApply` — were internals and have no replacement by design. Nothing about dispatch, reference counting or handle idempotence changed; this is a type and surface change only (API-001). Affects `src/types.ts`, `src/eventize-api.ts`, `src/index.ts`.
- **BREAKING (types):** `emitAsync()` returns `Promise<any[] | undefined>` instead of `Promise<any>`, on **all three** API surfaces — the standalone functions, `eventize.inject(obj)`'s methods and `Eventize#emitAsync()`. Every overload, both implementation signatures and the object surface in `src/types.ts` declared `Promise<any>`, while the runtime has always resolved to an array only when at least one listener returned a non-null value, and to `undefined` otherwise — a documented quirk with four specs behind it and a correct entry in `skills/using-eventize/SKILL.md`, which the code contradicted. `any` does not merely lose precision, it switches checking off: `(await emitAsync(ε, 'x')).map(…)` compiled and then threw on exactly the case the quirk describes, and because `any` is bidirectionally assignable, a surface implementing the already-narrowed `EventizeApi` did not catch it either. Narrowing the type immediately caught one imprecision in the library's own code — the empty branch returned the argument-less `Promise.resolve()`, which is `Promise<void>`, not `Promise<undefined>`. **Migration:** check the result before using it (`(await emitAsync(ε, 'x'))?.map(…)`, or a `?? []` fallback). The callers this breaks are the ones the quirk was already breaking at runtime. No runtime behaviour changed (TYPE-003). Affects `src/eventize-api.ts`, `src/eventize.ts`, `src/types.ts`, `src/__test-utils__/expect2ImplEventizeApi.ts`. One case in `src/documented-quirks.spec.ts` pins the narrowed type with a `@ts-expect-error` that starts failing the build if the signature is ever widened back, and one case per surface in `src/api-surfaces.spec.ts` pins it where "three surfaces, one implementation" is actually checked.
- **BREAKING (types):** `EventizedObject`'s marker slot is opaque, so `EventStore`, `EventKeeper` and `EventListener` are gone from `lib/index.d.ts`. The exported interface declared `[NAMESPACE]: {keeper: EventKeeper; store: EventStore}` inline, which made all three classes reachable from the published type — tsup inlined them into the emitted declarations, private method names included. `grep -c '^declare class' lib/index.d.ts` drops from 4 to 1; only `Eventize` remains. No consumer loses anything they could use: `EventStore` was never nameable, and the `NAMESPACE` key is a non-exported `unique symbol`, so the slot answered `TS7053` from outside either way — verified against the built declarations before and after. The boundary held in practice and now holds in the types. Internally everything reads the pair through `internalsOf()` in the new, unexported `src/internals.ts`, which carries the one cast the boundary costs; a second cast would mean the boundary is drawn wrong. **Migration:** code that annotated the slot structurally breaks. Nothing that calls the API does. Side effect: `getSubscriptionCount()` and `getRetainedCount()` shed a redundant cast and a defensive `?.` each — `isEventized()` is exactly the test that the slot is populated — which takes both files to 100 % branch coverage. Affects `src/types.ts`, `src/internals.ts` (new), `src/eventize-api.ts`, `src/getRetainedCount.ts`, `src/getSubscriptionCount.ts`.
- **BREAKING (types):** `ListenerType` is gone from the public surface. It was `export type ListenerType = unknown` — an alias for `unknown` that nothing in the package referenced, left behind when `EventListener.listener` was widened. It appeared in `lib/index.d.ts`'s export list, so removing it is a major-only move; anyone who imported it can write `unknown`. Affects `src/types.ts`.
- **Feature:** `Priority.Medium` (`1e3`) fills the gap the legacy `C` alias occupied — a value between `High` (`1e6`) and `Normal` (`0`) that no speaking name covered. The four legacy aliases `AAA`, `BB`, `C` and `Default` are now marked `@deprecated` in `EventizePriority`, so editors strike them through, and are slated for removal in a future major. They keep working. `EventizePriority` gains a required `Medium` member — anyone implementing the interface themselves (rather than reading the shipped `Priority` object, the normal use) needs to add it too; treated as a **Feature**, not **BREAKING**, since the interface exists to describe a constant this library ships. Affects `src/types.ts`, `src/Priority.ts`.
- **Feature:** `getRetainedCount(ε)` and `getRetainedEventNames(ε)` join `getSubscriptionCount(ε)`. The first reports how many events hold a retained value, the second every name carrying a retain policy whether or not it has fired — so `getRetainedEventNames(ε).length >= getRetainedCount(ε)` always holds. Until now the retained half of an emitter's state was only reachable through `ε[Symbol.for('eventize')].keeper`, which made retained-payload growth invisible from outside. Both return `0` / `[]` for non-eventized objects. New file `src/getRetainedCount.ts`.
- **Feature:** `unretain(ε, '*')` and `retainClear(ε, '*')` gained bulk semantics — the former drops every retain policy and every retained value, the latter drops the values and keeps the policies. Both were silent no-ops before, so nothing that worked stops working. An array containing `'*'` is treated as the wildcard regardless of what else it lists.
- **Feature:** `onceAsync(ε, eventNames, {signal})` accepts an `AbortSignal`. Aborting unsubscribes the internal `once()` handle and rejects the promise with the signal's `reason` when it has one, and with an `AbortError` `DOMException` otherwise — close to `fetch()`, but not identical: `abort(null)` also yields the `DOMException` here, where `fetch()` rejects with the `null` itself. Without a signal, an event that never fires kept the listener, the `resolve` closure and the caller's entire await continuation attached to the emitter for its whole lifetime, with no handle to release them: the unmount-before-event and cancelled-request shape. An already-aborted signal rejects without subscribing at all, and a retained event that resolves synchronously inside `once()` never attaches an abort handler in the first place. The parameter is optional, so no existing call changes. New exported type `OnceAsyncOptions`. All three API surfaces take it — the standalone `onceAsync(ε, …)`, the method installed by `eventize.inject()`, and the `Eventize` class method — which matters because the unmount-before-event shape is overwhelmingly a class-based one. Affects `src/eventize-api.ts`, `src/eventize.ts`, `src/types.ts`.
- **Fix:** An event name colliding with an inherited `Object.prototype` member no longer dispatches to it — on **both** dispatch paths, which is the only way to change it at all: `AGENTS.md` carries "both must funnel return values through the same `returnValue` callback" as an invariant, and a fix on one side would have made `emitAsync()` aggregate differently depending on whether the target was eventized. On the listener-object path, `emit(ε, 'toString')` called the inherited `toString` of every listener object subscribed to that name — and of every *wildcard* listener object, which by definition sees every name — so `once(ε, 'toString', {})` was consumed by the first emit without any user method running, and `emitAsync(ε, 'toString')` aggregated `'[object Object]'`. The duck-typing path for non-eventized targets had the identical hole one layer out: `emitAsync({}, 'toString')` resolved to `['[object Object]']`, and `emitAsync({}, 'constructor')` to `[{}]` — the `Object` constructor invoked as a plain function and its result collected. Bridge and plugin layers taking event names from external data (JSON keys, message types, DOM attributes) hit this without warning. Both paths now resolve the member through one shared `dispatchableMember()` helper that skips it when it is identical to `Object.prototype`'s member of the same name: `toString`, `toLocaleString`, `valueOf`, `constructor`, `hasOwnProperty`, `isPrototypeOf`, `propertyIsEnumerable`, plus V8's `__defineGetter__`, `__defineSetter__`, `__lookupGetter__` and `__lookupSetter__` — of those four, the two `__define*` ones threw `TypeError: Object.prototype.__defineGetter__: Expecting function` when invoked with arbitrary emit args, so a plain `emit(ε, '__defineGetter__')` used to take the process down, while the two `__lookup*` ones returned `undefined` and merely dispatched somewhere nobody asked for. Function identity is the whole test, which keeps the guard narrow: a target that defines its own method under that name — own property or anywhere up its prototype chain — dispatches as normal, and a `Object.create(null)` target has nothing to subtract. Aliasing the inherited function under its own name (`{toString: Object.prototype.toString}`) is skipped along with the inherited one, because nothing distinguishes the two and no caller wants the difference; four specs pin that edge — the own-property and prototype-chain shapes, once on the listener-object path and once on the duck-typed one — so the promise and the mechanism can't drift apart. A skipped name counts as unanswered, so it falls through to the `listener.emit(eventName, …)` / `obj.emit(eventName, …)` fallback rather than stopping — and a `once()` that reached neither survives, matching this release's rule that a dispatch which found nothing does not consume a one-shot subscription. The library already defended this exact spot against primitives (`isObjListener`, so that `on(ε, 'toFixed', 42)` misses `Number.prototype`); this is the same reasoning one prototype up. The method-name form `on(ε, 'evt', 'toString', obj)` is deliberately **not** guarded — it names the method, so the inherited hit is the caller's choice, and a spec now pins that boundary. **Migration:** an event name that was reaching an inherited `Object.prototype` method needs the method-name form (`on(ε, 'toString', 'toString', obj)`) or an own definition on the target; nothing else changes, because a subscription for such a name previously dispatched to code its author never wrote. Affects `src/utils.ts` (new `dispatchableMember()`), `src/EventListener.ts`, `src/eventize-api.ts`. 54 new cases in `src/EventListener.spec.ts` and `src/emit-ducktyping.spec.ts`, most of them generated from `Object.getOwnPropertyNames(Object.prototype)` so a host with more inherited methods than V8 is covered too.
- **Fix:** `off(ε, '*', listenerObject)` now detaches that object's wildcard subscriptions instead of doing nothing. `off()` sets its `forceRemove` flag whenever an event name arrives together with a listener object, which routes the call into `EventStore.removeByEventNameAndListenerObject()` — and that method searched `namedListeners`, where a wildcard listener has never lived: they sit in their own `catchEmAllListeners` array. So the call that reads literally as "unsubscribe this object from the wildcard" removed nothing and reported nothing, in every shape that can put an object on `'*'`: `on(ε, '*', obj)`, the bare catch-all `on(ε, obj)`, `on(ε, '*', fn, ctx)` and `on(ε, '*', 'method', ctx)`. The only workaround was `off(ε, '*')`, which wipes the whole emitter — retained state included, as of this release — or `off(ε, obj)`, which also drops the object's named subscriptions. The wildcard branch now filters `catchEmAllListeners` with the same predicate the named branch uses on its bucket, so the two agree on everything else: which registration shapes count as "that object", that every match in the bucket goes (two `once(ε, '*', obj)` calls are two listeners now, and both are removed), and that reference counting is not consulted — one call releases a `refCount`-2 registration outright, exactly as `off(ε, 'foo', obj)` always has. Two boundaries are pinned by spec because they are what makes this the *targeted* form: a **named** subscription of the same object survives — reach for `off(ε, listenerObject)` when you want both — and retained state is untouched, unlike the named sibling `off(ε, eventName, listenerObject)`, which unretains its whole event name. That difference needs no code: `retain()` rejects `'*'`, so the keeper call `off()` makes for it can never find an entry. **Migration:** code that called `off(ε, '*', obj)` as a no-op — knowingly or not — now loses that object's wildcard subscriptions. Nothing else was ever removed by it, so there is no other way this can bite. Affects `src/EventStore.ts`; 11 new cases in `src/off.spec.ts` and one in `src/lifecycle.spec.ts`.
- **Fix:** `off(ε, [eventName, …], listenerObject)` no longer clears retained state for listeners it never removed. `EventStore.remove()`'s array branch requires `listenerObject == null` — with one given, processing falls through to `removeByListener()`, where an array never matches a listener identity, so nothing is unsubscribed. The keeper branch in `off()` did not carry that condition, only `Array.isArray(listener)`, and called `keeper.remove()` for every name in the array regardless. Measured against an emitter with one subscription and two retain policies: `off(ε, ['a', 'b'], listenerObject)` left the store at its original subscription count while the keeper's retained values and policies both dropped to zero — the one remaining call shape in which store and keeper disagreed about what a call had done, present since the array form's `v4.0.0` introduction and not introduced by this release's other `off()` changes. The keeper's array branch now shares the store's `listenerObject == null` guard, making the whole call a genuine no-op on both halves, matching what it already did to the listener registry. The sibling named form, `off(ε, eventName, listenerObject)`, is unchanged and deliberately so — see the "known asymmetries" note in `AGENTS.md`: there the store *does* detach a listener via `forceRemove`, so unretaining the name is not the mismatch this fix addresses. **Migration:** code that called this shape expecting it to reset retain state (it never detached the listener either way) must call `off(ε, [names])` without a listener object, or `unretain(ε, [names])`, instead. Affects `src/eventize-api.ts`. One case in `src/off.spec.ts` (COR-001).
- **Fix:** A consumed unsubscribe handle no longer holds the emitter, nor the listener. `makeUnsubscribe()` tracked its consumed state in a separate boolean and kept its captured references for the lifetime of the handle, so calling a handle released the *listener* — `EventListener.detach()` nulls its fields, and the listener object was demonstrably collectable — while the closure went on pinning the emitter itself, and through it the `EventStore`, the `EventKeeper` and every retained payload the keeper holds. The blast radius is the pattern this project's own docs recommend: `subs.push(on(…))` followed by `subs.forEach((u) => u())` on teardown, with the array outliving the component. A kept handle for one event name was enough to keep a retained buffer alive under a completely *different* name — the handle never touched that name, it merely kept the emitter reachable. Both captures, the emitter and the listeners, now live in **one** slot that the first call nulls, which keeps the single-shot guarantee intact (a second call finds nothing to release), makes the null test double as the consumed flag, and makes the release unconditional: it happens whether or not the `off()` actually detached the listener, because reference counting governs the listener, not the closure. It was `EventName | EventName[] | Array<[EventName, number]>`, which allowed a list of names _or_ a list of `[name, priority]` tuples but not a mix — even though the runtime checks `Array.isArray()` per element and handles the mixed form fine. It is now `EventName | Array<EventName | EventNameWithPriority>`, so `on(ε, [['foo', 100], 'bar'], fn)` type-checks without a cast. The new `EventNameWithPriority` (`[eventName: EventName, priority: number]`) is exported from the package root. `AnyEventNames` is unchanged and still used by `emit()` / `retain()`, which have no notion of priority.
- **Types:** Per-event priorities now work on **typed** emitters. Previously the tuple form didn't type-check there at all: the typed overloads accepted only `K` / `K[]`, and the loose fallback was closed off because `NonTypedEmitter<T>` collapses to `never` for a branded emitter. The typed array overload of `on()` / `once()` (and the corresponding `SubscribeFunc` signatures used by the injected and class APIs) now accepts `Array<K | [K, number]>` plus an optional call-level priority. Event names inside tuples are still narrowed against the event map, so `on(ε, [['unknown', 0]], fn)` remains a compile error. Widening a parameter position only — no call that compiled before stops compiling.
- **Docs:** Corrected a claim that predates this release: `off(ε, eventName)` doesn't merely clear the retained _value_, it drops the retain _policy_ as well, so it behaves like `unretain()`. `README.md`, `docs/off.md`, and the skill now say so.
- **Tests:** `src/documented-quirks.spec.ts` grew to 15 cases — symbol/string parity between the scalar and array `off()` forms, the listener-array regression guard, mixed tuple/name arrays on plain and typed emitters, the call-level-priority combination, and two `@ts-expect-error` cases proving tuples still reject unknown event names.

## `v5.0.0` (2026-05-13) — Duck-typed `emit()` / `emitAsync()`

- **BREAKING:** `emit()` and `emitAsync()` no longer throw `"object is not eventized"` when called on a non-eventized target. Instead, they fall back to duck-typing — the same pattern already used by the listener-object dispatch path (`EventListener.ts`):
  1. If `obj[eventName]` is a function, call it with the args (with `this === obj`).
  2. Otherwise, if `obj.emit` is a function, call `obj.emit(eventName, ...args)`.
  3. Otherwise, silently no-op.
     Return values are funneled through the same aggregation pipeline as eventized listeners, so `emitAsync()` collects them uniformly. `null` / `undefined` / non-object targets silently no-op. The `'*'` wildcard still throws — it remains subscribe-only. **Migration:** callers that relied on `emit()` / `emitAsync()` throwing as a typo-safety net should add an explicit `isEventized()` guard (or a TypeScript typed emitter, which still rejects unknown event names at compile time).
- **Unchanged (strict):** `retainClear()` and `unretain()` continue to throw `"object is not eventized"` — they operate on internal retain state that does not exist on plain objects and has no meaningful duck-typed equivalent.
- **Types:** Public overload set unchanged. The existing typed-emitter overload still binds first for `EventizedObject<TEvents>`, and the loose `NonTypedEmitter<T>` overload accepts plain objects — types now match runtime exactly.
- **Tests:** New `src/emit-ducktyping.spec.ts` (28 cases) covers method-with-args, `this` binding, symbol event names, `.emit()` fallback, missing-method silent no-op, array forms with mixed method/fallback, wildcard rejection, non-object targets, `retainClear`/`unretain` strictness, and the full `emitAsync()` return-aggregation pipeline (sync value, Promise, array-of-Promises, null, undefined, no-op). Existing `emit.spec.ts › duck typing` case flipped to assert non-throw.
- **Docs:** README _Auto-eventize vs. strict mode_ table and examples updated; `skills/using-eventize/SKILL.md` quirks #1 and #4 (forwarding caveat) revised.
- **Affected files:** `src/eventize-api.ts`, `src/emit-ducktyping.spec.ts` (new), `src/emit.spec.ts`, `README.md`, `skills/using-eventize/SKILL.md`, `package.json` (`4.3.1` → `5.0.0`).

## `v4.0.0` (2024-07-22)

**!! BREAKING CHANGES !!**

_Introduction of the new functional API_

Previously, the Eventize API methods were assigned to the object as methods after calling `eventize(obj)`
This behavior has changed in 4.0.0: all eventize methods are now available as library exports in the functional variant:

```js
import {
  on,
  once,
  onceAsync,
  off,
  emit,
  emitAsync,
  retain,
  retainClear,
} from '@spearwolf/eventize';
```

| before         | after            |
| -------------- | ---------------- |
| `obj.on(..)`   | `on(obj, ...)`   |
| `obj.once(..)` | `once(obj, ...)` |
| `obj.emit(..)` | `emit(obj, ...)` |
| `obj.off(..)`  | `off(obj, ...)`  |
| ...            | ...              |

There is still the option to inject the Eventize API as methods to the object (but this is no longer the default) by using:

- `eventize.inject(obj)` &rarr; _eventizedObj with eventize-api methods_
  - the `eventize.extend()` method has been removed, however
- `new (class extends Eventize {})()`
  - the base class `Eventize` is still available and works in the same way as before

If you are using the syntax from the _composition via inheritance_ example, you should now be using `eventize.inject` directly:

```typescript
import {eventize, type Eventize} from '@spearwolf/eventize';

export interface Foo extends Eventize {}

export class Foo {
  constructor() {
    eventize.inject(this);
  }
}
```

Other API Changes

- The _default export_ is still the `eventize()` function, but the `Priority` object is no longer assigned here
  - `Priority` is still available as a named export (only)
