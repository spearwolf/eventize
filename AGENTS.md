# AGENTS.md

Canonical guide for coding agents in this repo. `CLAUDE.md` is a symlink to this file — edit only this one.

`@spearwolf/eventize` makes any JS/TS object a **synchronous** event emitter. Zero runtime deps, ESM + CJS, opt-in typed event maps. All development happens in `src/`; `lib/` is build output.

## Versioning right now

`package.json` carries **`6.0.0-dev`**. The registry is on `v5.1.0` — no `6.x` has ever been published, and the `-dev` suffix is what keeps it that way: `scripts/publishPackage.cjs` exits before `npm publish` for any version ending in `-dev`. **Do not drop the suffix, and do not bump the version.** Releasing is a human's call.

Two consequences:

- **Everything unreleased goes under `## \`v6.0.0\` (unreleased)` in `CHANGELOG.md`** — one section, no new version headings above it. A change that would ordinarily demand a major only widens what that section already carries; nothing inside it can break a consumer who has never had a `6.x`.
- **Version references in prose are `v5.1.0` or `v6.0.0`, never anything between.** "Since v6.0.0" for what this release introduces, "up to v5.1.0" for what it replaces. The intermediate versions reached nobody, and naming one sends a reader looking for an upgrade path that does not exist.

## Verification

`npm run cbt` — clean → build → `typecheck` (`tsc --noEmit`) → `attw --pack` → test with coverage → lint → format check. Run it before declaring a task done.

Two things about it worth knowing:

- **`typecheck` is the only cache-independent type check.** esbuild (the JS bundle) and tsup's dts pass never type-check, and `attw --pack` only checks that already-emitted declarations resolve. `tsc --noEmit` against `include: ["src"]` is what actually reads every source file.
- **`cbt` is the only local run where `coverageThreshold` binds** — it runs `test:coverage`. Bare `npm test` collects no coverage on purpose, so a narrow loop over one spec file doesn't fail a global threshold. CI runs `cbt` too, so the threshold is enforced in exactly one place. Raise the numbers when coverage rises; never lower them to make a build pass.

Narrower loops: `npm test -- src/once.spec.ts`, `npm test -- -t "retains the last value"`, `npm run watch`.

**`npm run clean` clears the ts-jest cache too, and that is not optional.** Besides `lib/`, `build/`, `dist/`, `types/` and `tmp/` it runs `jest --clearCache`, because ts-jest's transform cache lives outside the repo — `/tmp/jest_rs` on Linux — and used to survive every clean, every `npm ci` and every `cbt`. A stale cache serves previously compiled output and hides type errors a fresh checkout hits immediately; it once produced a green `cbt` for a change that broke 13 of 25 spec suites, and the breakage survived two reviews because both trusted the green bar. `cbt` runs `clean` first, so the gate can no longer be passed by a cache. Don't take it back out to make `cbt` faster — the seconds it costs are the seconds that bought that bug.

**`typecheck` and the test compile don't use the same module resolution.** `tsc` honors `tsconfig.json` (`module: esnext`, `moduleResolution: bundler`); ts-jest forces `module: commonjs` and, because `bundler` only pairs with `commonjs` on TypeScript ≥ 6, silently substitutes `node10`. They agree only because every import in `src/` is relative and extension-free. A `nodenext`-style subpath import or a `paths` remap would break that, and `typecheck` passing would stop guaranteeing the test compile does.

**TypeScript is pinned below 7, on purpose.** `ts-jest` compiles every spec and peers on `typescript: ">=4.3 <7"`; `typescript-eslint` caps at `<6.1.0`. Check both with `npm view <pkg> peerDependencies` before retrying, and do not force past a real peer conflict with `--legacy-peer-deps`, `--force` or an `overrides` entry — that trades a known state for one nothing in the toolchain has agreed to support.

## Architecture invariants

These are the things that bite. Everything else is readable from the source, and the deeper reasoning behind the store's clone-on-mutate design lives in the doc comments in `src/EventStore.ts`.

**The eventized marker.** `asEventized(obj)` attaches a property keyed by `NAMESPACE` (`Symbol.for('eventize')`) holding `{protocol, keeper, store}`. That hidden slot _is_ the definition of an emitter — `isEventized()` just probes for it. This is why eventize works on plain `{}`, existing objects and class instances interchangeably, and why nothing may ever enumerate its way onto the public surface. The slot is defined with all three descriptor flags at their `false` default — not enumerable, not writable, **not configurable**. The last one is load-bearing: while it was `true`, `delete ε[Symbol.for('eventize')]` was legal and its consequences were entirely silent, the object reading as non-eventized while store and keeper went on holding listeners and retained values nothing could reach.

**The protocol version is what makes the realm-wide key survivable.** `Symbol.for()` is registered per realm, so *every* copy of this library writes and reads the same slot, and npm resolves a `^5` and a `^6` side by side the moment one transitive dependent asks for the older range. Each copy then reads the other's payload as its own — up to v5.1.0 that mixture dispatched happily across versions and only broke calls later, from inside the dispatch, with a `TypeError` naming neither eventize nor the cause. `PROTOCOL_VERSION` (`src/constants.ts`) rides in the payload and `internalsOf()` compares it. Three rules hold that in place:

- **The success path stays one property load and one compare.** `internalsOf()` is on every `on`/`emit`/`off`. The throw lives in a separate function so the message building never enters the hot path's bytecode.
- **`internalsOf()` is the only checkpoint, and that is why `asEventized()` calls it for effect.** On the `isEventized()` early exit it discards the return value and keeps the throw — returning a foreign emitter silently hands the caller an object that breaks somewhere else entirely. It is also what keeps the one-cast rule intact: reading the slot a second way to check it would buy a second cast.
- **`isEventized()` never throws and never learns about protocols.** It is a type guard, and "eventized" is a different question from "eventized by *this* copy". The second one belongs to the public `getEventizeProtocol()`, which reads the slot defensively, returns `number | undefined` and never throws — it exists to be called *before* the bang, so it cannot be the thing that goes bang. Bump `PROTOCOL_VERSION` when the payload stops being drivable by the previous major, not for every breaking change.

In the **types** the slot is opaque: `EventizedObject` declares it as a branded empty shape, and the real `{keeper, store}` lives in `src/internals.ts`, which `src/index.ts` does not re-export. Declaring the pair inline made `EventKeeper`, `EventStore` and — through the store — `EventListener` reachable from an exported type, so tsup inlined all three into `lib/index.d.ts`. Everything internal reads them through `internalsOf()`, which holds **the one cast** this boundary costs; needing a second one means the boundary is drawn in the wrong place. `grep -c '^declare class' lib/index.d.ts` must stay at 1 (`Eventize`).

**Two collaborators per emitter.** `EventStore` is the listener registry (binary-search insertion by priority, removal via `(listener?, listenerObject?, forceRemove?)`). `EventKeeper` is the retained-events log. One ordering rule is worth protecting: `subscribeTo` collects retained events into a local `retainedEvents[]` and `EventKeeper.publish()` flushes them **after** registration completes, so a new subscriber sees replayed values as a batch rather than mid-registration. (The order within that batch is emit *completion* order — see the retain quirk under Known asymmetries.) `EventListener.callAfterApply` means "discharge pending one-shot obligations", not "release a handle" — it runs from inside `EventListener.apply()`, i.e. inside the dispatch walk, and the drop it can trigger (a listener left with `refCount === 0` and no obligations remaining) routes through `bucketForMutation()` like every other bucket change, because a live `forEach()` may be stepping through the bucket it drops from.

**`EventStore` clone-on-mutate — the held-count protocol.** `forEach()` walks the **live** buckets; it does not copy them. What protects a walk from a listener that subscribes or unsubscribes inside its own callback sits on the mutating side instead. A bucket is not a bare array: `ListenerBucket` carries a count of the walks currently stepping through it under a module-private symbol; `forEach()` counts itself in and out again in a `finally`; and `bucketForMutation()` clones a bucket if and only if that count is non-zero, swapping the clone into `namedListeners` — or into `catchEmAllBucket` — while the walk keeps the array it started on.

The question is not "is a walk running" but "is a running walk holding *this* array". A `forEach()` holds at most two arrays; every other bucket may change in place at any time, dispatch or no dispatch. The rules that fall out, all load-bearing:

- **Every array that can become a bucket is born in `createBucket()`** — including the clone. A hand-rolled `slice(0)` arrives without the count field, takes a different hidden class, reads as *held* (`undefined === 0` is false), and buys one copy it does not owe, which installs a well-formed clone and hides the mistake for good.
- **A bucket never equals a plain array literal.** The symbol key is invisible to `Object.keys()`, `for…in`, spread and `JSON.stringify`, but `Reflect.ownKeys()` sees it and so does Jest, whose `toEqual` / `toStrictEqual` compare own enumerable symbols. **Compare buckets by identity and length.**
- **It is a count, not a flag.** Nested emits over the same bucket each add one and take their own back; a boolean would let an inner walk's exit tell the store the outer one is over. A walk counts *both* of its buckets, named and wildcard.
- **The count is given back from a `finally`.** A listener that throws must not leave a dead walk counted in, or every later mutation of that bucket clones forever.
- **An empty bucket is never counted, because `forEach()` skips it.** A wildcard subscription taken during a named dispatch goes in place and costs nothing; the running dispatch still never sees it.
- **Route every content change through `bucketForMutation()`, and call it only once a mutation is certain.** Splicing a live array directly makes a mid-dispatch subscription visible to the running emit again. Calling it speculatively is the opposite failure: a dedup in `add()` or a removal that matches nothing must leave bucket identity alone, or "identity changed" stops meaning "the registry changed" and the specs that measure clone counts stop measuring anything. The removal loops therefore call it at the first match, not before.
  - **The one exception is truncation.** `removeByEventName()` and `removeAllListeners()` do not *change* a bucket, they let go of it — the map entry is deleted or the map cleared. The `bucket.length = 0` on top is a courtesy to a caller still holding the array from `getListenersForEventName()`, and both skip it when a walk is stepping through that very array. Without that skip, `emit()` throws the internal hole-guard `Error` at the caller in a merge dispatch. Cloning a bucket in order to truncate the clone and drop it would be theatre — don't "fix" these two into the routed path.
- **The clone's destination is derived from the array, not from the event name.** `bucketForMutation()` compares the bucket against `catchEmAllBucket`. Deriving it from the name would send the clone of a `'*'` key in `namedListeners` — which the public `getListenersForEventName('*')` creates on demand — into the wildcard slot. That is unreachable rather than merely untested, and no spec can catch a swap; keeping the derivation on the array is what keeps the question closed.
- **The merge loop lives in `mergeWalk()`, outside `forEach()`.** `forEach()` carries a `try`/`finally`, which puts it near TurboFan's inlining budget, so its bytecode size decides whether its callers inline it. Inlining the merge loop back measured as a real regression. Keep `forEach()` small — anything added to it is paid on every dispatch, including those that never reach the new code.
- **`getListenersForEventName()` creates buckets lazily and hands out live references.** A reference held across a mutation may be the pre-clone array. `add()` is its only caller outside the specs and uses the bucket immediately; the specs call it directly on purpose, because reaching a bucket the store has not created yet — an untouched name, the `'*'` key, an array a spec means to punch holes into — is exactly what the reading door will not do. That door is `peekListeners()`, added in v6.0.0 for a caller that only wants to look: it creates neither a bucket nor a map entry, answers an unknown name with one shared frozen empty array, and reads `catchEmAllBucket` for `'*'` rather than the impostor key. For a name it does know it hands back the very same live array, only `ReadonlyArray`-typed — the no-mutation promise is the return type, not a runtime copy, so the pre-clone trap above applies unchanged, and nothing here promises the reference stays fresh across a later mutation.

Benchmarking this area has two traps: two library variants loaded in one process make the call site polymorphic and shift results by double digits, and `mergeWalk()` wants a process of its own. Quote ranges, not cells — individual cells move by ten points between runs.

**Three API surfaces, one implementation** (`eventize-api.ts` → `eventize.ts`). Standalone functions, `eventize.inject(obj)` methods and `class Eventize` all delegate to the same `on`/`emit`/`off`. Never fork logic into a surface. The class/inject side casts to loose implementation-shape signatures on purpose — the public overload sets are tuned for end users and don't accept a spread of `SubscribeArgs`.

**Two dispatch paths in `emit`.** `_emit` handles eventized targets; `_duckEmit` handles non-eventized ones (`obj[eventName](...args)`, then `obj.emit(eventName, ...args)`, then no-op). Three things must hold on both sides, or `emitAsync` aggregation silently diverges between them: both must reject `'*'`, both must funnel return values through the same `returnValue` callback, and both must resolve the event-named member through `dispatchableMember()` (`utils.ts`) rather than reading `target[eventName]` raw — that is the `Object.prototype` boundary, and a path that skips it answers `emit(ε, 'toString')` while the other doesn't. `emitAsync` differs from `emit` only in that aggregation; invocation is always synchronous.

**`subscribeTo` and `types.ts` move in lockstep.** `_subscribeTo` decodes the overloaded `on()` shapes positionally. Changing the API means changing `SubscribeArgs` _and_ the parsing. What may enter the store is decided by `detectListenerType()` (exported from `EventListener.ts`, and the same tag `EventStore.isSimilar()` compares) plus a falsy test in front of it — a new listener shape has to be added there, not at the call site, or it will be rejected before it reaches a listener instance. The priority check is `Number.isNaN`, never `Number.isFinite`: `Priority.Max` / `Priority.Min` are `±Infinity`.

**Counters are per module instance.** `EventListener.lastId` (secondary sort among equal priorities) and `EventKeeper.nextOrderId` (replay order of retained events) are module-global `let` variables. Loading the ESM and the CJS build in the same process gives two independent counter pairs, so ordering stability is guaranteed per loaded module instance, not per realm. This is deliberate: the `Symbol.for('eventize')` marker is realm-wide because identity must be; the counters are not, because sorting only ever compares listeners on the same emitter, and one emitter comes from one module instance.

A third counter, `nextObligationSequence` in `EventListener.ts` (the `once()` obligation sequence `EventStore.settleOneShots()` compares a dispatch's watermark against), gets the same module-instance scoping but not the same free pass. `lastId` and `nextOrderId` are safe because every comparison they feed stays inside one emitter, and one emitter's listeners are all `new EventListener()`'d by the same module instance. The obligation counter cannot make that assumption: `asEventized()`'s marker is realm-wide by design, so if both builds are loaded against the same objects, a store obtained from one module instance can still receive a listener constructed by the other — `EventStore.add()` matches structurally, not by module identity — and an obligation stamped by a foreign instance's counter can end up compared against a watermark read from this instance's counter. Where a mis-ordered `lastId` only reorders equal-priority listeners, a foreign `sequence` that is numerically ahead of the watermark never satisfies `sequence < watermark`, so the obligation never discharges — a `once()` that fires on every emit instead of settling once. Loading both builds against the same eventized objects is unsupported for exactly this reason, not merely for the ordinary counter-scoping reason above.

**The protocol check does not cover this case, and cannot.** It compares versions, and the ESM and CJS builds of one version carry the same `PROTOCOL_VERSION` — they are the same library, twice. What it catches is the *other* copy: a different major sharing the realm-wide marker key. Two module instances of one major stay a documented "don't", enforced by nothing.

## Known asymmetries

Verified quirks that look like bugs but are load-bearing or simply undocumented. Don't "fix" them without a CHANGELOG entry.

- `off(ε, name)` doesn't merely clear the retained *value* — `keeper.remove()` drops the retain *policy* too, so it behaves like `unretain()`. Later emits of that event are not retained until `retain()` is called again.
- The array branch of `off()` is reached from exactly one direction since v6.0.0: an explicit `off(ε, [name, …])`. The unsubscribe function of a multi-event `on()` used to be a second, passing an array of `EventListener` instances through it; `makeOnUnsubscribe()` calls `store.release()` per listener now and never enters `off()`. The `isEventName` filter on that array stays anyway — the surviving caller hands in a consumer-assembled list, and the filter is what keeps symbol event names (a `typeof === 'string'` test silently dropped them) while ignoring anything that is not a name. An array containing `'*'`, `null` or `undefined` never reaches this branch: `isBulkRemoval()` sends it to the bulk path first. That predicate mirrors `EventStore.remove()`'s *effective* array behaviour, not its condition: the store forwards each element back into itself with a null listener object, so one nullish element lands in the wipe-everything branch. Anything else deciding "is this argument bulk?" has to reproduce that, not just test for `'*'`.
- `on()` and `once()` aggregate onto the same identity key, in either order, since v6.0.0. `EventStore.add(listener, obligation)` takes the registration's obligation instead of a kind flag: `null` for a persistent `on()`, which increments `refCount`; an `OnceObligation` for a `once()`, which is pushed onto the target listener's `onceObligations` array (lazily created, `undefined` when empty). A listener is alive while `refCount > 0 || onceObligations !== undefined`. The first dispatch that reaches the listener discharges every obligation stamped before that dispatch began, together, from `EventStore.settleOneShots()` — so two `once()` calls on one identity fire once, not twice, and an `on()` on the same identity keeps the registration alive independently of any obligations riding on it. Up to v5.1.0 the fold went one way only (`once(); on()` collapsed, `on(); once()` did not), and the collapsed listener fired on every emit with no handle able to release it — the second `callAfterApply` installed overwrote the first, so one emit decremented `refCount` from 2 to 1 and the survivor's own idempotence guard could never take it to 0.
- `emitAsync()` resolves to `undefined`, not `[]`, when no listener returned a non-null value.
- `emit()` on a non-eventized target does not throw. Typo safety comes from typed emitters or an explicit `isEventized()` guard.
- No recursion guard. `A → B → A` forwarding and same-event re-emission overflow the stack by design — the v4.2 guard forbade legitimate patterns and was reverted.
- **Any** nested `emit()` retains in completion order, not start order: `keeper.retain()` runs after the dispatch, so nested calls write on unwind, innermost first. Forwarding is the common way in, not self-recursion. Self-recursion is the case that surprises most, because both calls compete for one slot and the outermost value wins. The write must stay after the dispatch — that is what keeps a throwing listener from destroying the previously retained value.
- `off(ε, undefined)` is not a no-op — it takes the same branch as `off(ε)` and removes **every** listener plus **all** retained state. Cleanup code that forwards a possibly-missing value through (`off(ε, handlers[name])`) wipes the emitter when the lookup misses. Guard the call, or keep the `on()` handle and call that.
- The unsubscribe handles from `on()` and `once()` are single-shot, and no longer share one shape: `makeOnUnsubscribe()` nulls its captured emitter before calling `store.release()` on each listener it holds; `makeOnceUnsubscribe()` nulls its capture before calling `store.releaseObligation()` on the one `OnceObligation` it holds — no listener list, because the obligation already knows every listener it was added to. Either way a second call is inert. Not cosmetic — `on()`'s reference-counted dedup and `once()`'s obligation aggregation both mean several handles can share one `EventListener`, and without the guard one handle called twice released a sibling's share. `releaseObligation()` carries a second, independent guard: it no-ops once `obligation.settled` is true, so a handle kept past the dispatch that already discharged its obligation finds nothing left to release — the obligation's `settled` flag is the generation check that does for a `once()` handle what the nulled capture already does for the handle itself. It runs in the other direction too, and has to: `OnceObligation.onSettled` is a hook `makeOnceUnsubscribe()` installs and `dischargeObligation()` clears and calls, so the dispatch that spends a `once()` nulls its handle's capture even though nobody touched the handle. Up to `v5.1.0` that fell out of `once()` wiring its own unsubscribe into `callAfterApply`; that slot settles obligations now, so the release needs somewhere else to hang. A handle made *after* its obligation was already discharged — a retained replay settles it from inside `subscribeTo()` — nulls its capture on the spot instead, because a hook installed then would never run. The nulled capture doubles as the consumed flag on purpose: a separate boolean would leave the emitter in the closure of every kept handle, which is the leak this design exists to prevent. Emitter and listener (or obligation) live in **one** slot and are nulled together, so a single null test releases and narrows both.
- **A spent handle holds nothing; an *unconsumed* one still pins the emitter, by design.** An `on()` handle is spent by being called. A `once()` handle is usually spent by something else entirely: the dispatch that discharges its obligation, whether that is an `emit()` or a retained replay that discharged it before the handle existed. So a `once()` whose event fired holds nothing without anyone touching it, and a `once()` that ended any other way — `off(ε, 'foo')` before it fired — never reached a discharge and goes on pinning. An emitter subscribed to itself parks the back-reference in a different slot per spelling: `listener` for `on(ε, 'foo', ε)` and `on(ε, ε)`, `listenerObject` for `on(ε, 'foo', 'method', ε)`. A release that clears one field and not the other frees some of those and leaks the rest.
- `retain(ε, [name, …])` rejects a wildcard atomically: nothing is retained if `'*'` appears anywhere in the array. `emit(ε, [name, …])` does not — it dispatches the names preceding `'*'` and then throws. Unify them only with a CHANGELOG entry. `on(ε, [name | [name, priority], …])` sides with `retain()`: `_subscribeTo()` resolves every per-event priority into one list and validates it before the first `register()` call, so a `NaN` in the last tuple leaves nothing subscribed.
- `retain()`, `unretain()` and `retainClear()` treat `'*'` specially, but not identically: `retain(ε, '*')` throws — `'*'` stays subscribe-only, matching `emit()`. `unretain(ε, '*')` and `retainClear(ε, '*')` instead mean "all retained events": the former drops every retain policy and every retained value, the latter drops only the values and keeps the policies.
- The `Object.prototype` boundary covers two of the three member lookups, on purpose. `dispatchableMember()` (`utils.ts`) skips a member identical to `Object.prototype`'s same-named one, and both the listener-object branch of `EventListener.apply()` and `_duckEmitOne()` route through it — they have to agree, or `emitAsync` aggregates differently for eventized and non-eventized targets. The method-name branch (`listenerObject[listener]`) does **not**: `on(ε, 'evt', 'toString', obj)` spells the method out, so the inherited hit is the caller's choice.
- `off(ε, eventName, listenerObject)` unretains the *whole* event name — value and policy — even though it only detaches one listener object's subscription and leaves any sibling listener for that name subscribed. Deliberately not scheduled to change; `git log -L` shows the branch unchanged since the 4.0.0 functional API, so fixing it now would be breaking. See `docs/lifecycle.md`. The array sibling, `off(ε, [eventName, …], listenerObject)`, is **not** the same case: `EventStore.remove()`'s array branch requires `listenerObject == null`, so with one given the store never detaches anything, and the keeper mirrors that condition — a complete no-op on both halves. Don't fold the two together; the named form still detaches a listener via `forceRemove`, the array form never did.
- `off(ε, '*', listenerObject)` is a *targeted* removal, not a bulk one, and `EventStore.removeByEventNameAndListenerObject()` special-cases the wildcard to make it one: `'*'` is not a key in `namedListeners`, so the branch searched a bucket wildcard listeners can never be in. Two boundaries hold it in place: a **named** subscription of the same object survives — `off(ε, listenerObject)` is the form that takes both — and retained state is untouched, which needs no code of its own because `retain()` rejects `'*'`. Reference counting is not consulted, so one call releases a `refCount`-2 registration.
- The "equal priorities keep insertion order" guarantee holds only within a bucket. `sortByPriorityAndId` breaks a priority tie on ascending `id`, but only ever between listeners of the same kind (named-for-one-event, or wildcard). The merge in `EventStore.forEach()` compares `cur.priority >= other.priority` and never looks at `id`, so at equal priority the named listener always goes first, independent of registration order. Deliberate scope limit, not a bug: `forEach()` is not to be changed to consult `id` across the bucket boundary.

## Conventions

- Specs live next to sources as `*.spec.ts`; Jest `testMatch` is restricted to `src/**`.
- Every feature or bugfix gets a spec.
- **This file states behaviour, never coverage.** What the library does belongs here; which spec pins it does not. A test inventory written in prose goes stale the moment someone moves a case, and it goes stale silently — a reader who finds one such claim wrong has no way to tell which of the others still hold. Guarantees are the specs' job, and a spec that needs explaining explains itself in a comment beside the case.
- **Important enough to state is important enough to test.** A constraint that matters gets a spec. A constraint that does not matter gets no spec, no documentation and no line here. There is no third category, and "documented but untested" is the shape every stale claim starts as. The public API is the law; the specs interrogate the behaviour, including the parts no signature shows.
- Relative imports carry no extension — `tsup` writes the output extensions.
- `lib/` is generated and git-ignored. Never edit it, never read it to answer a question about behavior.
- **No issue identifiers in the repo.** `PERF-001`, `BUG-123` and the like belong to whatever tracker or report produced them and mean nothing once it is gone. A comment must say what it means on its own; work that outlives the conversation goes in `docs/backlog.md` under a descriptive name.

## Documentation obligations

Progressive disclosure applies to this repo's own docs — the deep material lives in `docs/` and the agent-facing reference in `skills/using-eventize/references/`. Touch what the change actually affects:

| Change | Update |
| --- | --- |
| Public API or runtime behavior | `CHANGELOG.md`, under `## \`v6.0.0\` (unreleased)` |
| Anything breaking against `v5.1.0` | `docs/migration.md` as well — with the grep pattern and the replacement, not just the fact |
| Documented behavior or an example | `README.md`, plus the matching `docs/*.md` if the detail lives there |
| Dispatch semantics, retain behavior, or any quirk above | `skills/using-eventize/` — `SKILL.md` for the summary, `references/*.md` for detail |
| Cleanup, retain lifetime, or handle semantics | `docs/lifecycle.md`, plus a case in `src/lifecycle.spec.ts` |
| Deferring a fix, or accepting a known defect | `docs/backlog.md` — the decision and its reason, not a ticket number |
| Purely internal refactor | nothing |

Two rules about how, not what:

- **`skills/using-eventize/` must stay self-contained.** It gets symlinked into a user's agent directory, where a path out of the folder resolves to nothing. Everything it references lives under `skills/`; duplicating a paragraph from `docs/` is the correct trade.
- **`CHANGELOG.md` is a record, not an essay.** One to three lines per entry: what changed, and for a breaking change what to write instead. Rationale, benchmark numbers and internal mechanics belong in the code comments or in this file.

Docs are English. Prefer stating the gotcha over restating the signature.
