# AGENTS.md

Canonical guide for coding agents in this repo. `CLAUDE.md` is a symlink to this file — edit only this one.

`@spearwolf/eventize` makes any JS/TS object a **synchronous** event emitter. Zero runtime deps, ESM + CJS, opt-in typed event maps. All development happens in `src/`; `lib/` is build output.

## Versioning right now

`package.json` carries **`6.0.0-dev`**. The registry is on `v5.1.0` — no `6.x` has ever been published, and the `-dev` suffix is what keeps it that way: `scripts/publishPackage.cjs` exits before `npm publish` for any version ending in `-dev`, so a push to `main` runs the full test matrix and builds the package without releasing it. **Do not drop the suffix, and do not bump the version.** Taking it to `6.0.0` is the release act, and it belongs to a human.

Two consequences for anything you write:

- **Everything unreleased belongs under `## \`v6.0.0\` (unreleased)` in `CHANGELOG.md`** — one section, no new version headings above it. A change that would ordinarily demand a major only widens what that section already carries; nothing inside it can break a consumer who has never had a `6.x`.
- **Version references in prose are `v5.1.0` or `v6.0.0`, never anything between.** "Since v6.0.0" for what this release introduces, "up to v5.1.0" for the behaviour it replaces. The intermediate versions this work passed through reached nobody, and naming them in a migration note sends a reader looking for an upgrade path that does not exist.

## Verification

`npm run cbt` — clean → build → `typecheck` (`tsc --noEmit`) → `attw --pack` → test with coverage → lint → format check. Run it before declaring a task done. `typecheck` is the gate that catches dual-format type breakage cache-independently: esbuild (the JS bundle) and tsup's dts pass (the `.d.ts` rollup) never type-check, and `attw --pack` only checks that already-emitted declarations resolve, not the source — `tsc --noEmit -p tsconfig.json` against `include: ["src"]` is what actually reads every file under `src/`, unaffected by the ts-jest transform cache described below. `cbt` is also the only local run where the `coverageThreshold` actually binds.

`typecheck` and the test compile don't type-check under the same module resolution, and that's fine only by accident of this codebase's import style. `tsc --noEmit` honors `tsconfig.json` as written — `module: esnext`, `moduleResolution: bundler`. ts-jest's compile path forces `module: commonjs` on every non-ESM run regardless of that setting, and since `bundler` only pairs with `commonjs` on TypeScript ≥ 6 while this project pins TypeScript at 5.9.x, it silently substitutes `moduleResolution: node10` for the actual test compile (`ts-compiler.js`'s `resolveCompatibleModuleResolution`, closing ts-jest#4198). The two paths agree here only because every import in `src/` is relative and extension-free, which resolves identically under `bundler` and `node10`; a `nodenext`-style subpath import or a `paths` remap would not, and `typecheck` passing would no longer guarantee the test compile does too.

Narrower loops while working: `npm test -- src/once.spec.ts`, `npm test -- -t "retains the last value"`, `npm run watch`. Bare `npm test` collects no coverage on purpose — a threshold applied to one spec file fails for the wrong reason.

**`npm run clean` does not clear the ts-jest cache.** It removes `lib/`, `build/`, `dist/`, `types/` and `tmp/`. ts-jest's transform cache lives outside the repository — `/tmp/jest_rs` on Linux — and survives every clean, every `npm ci`, and every `cbt`. A stale cache serves previously compiled output and hides type errors that a fresh checkout or a CI runner hits immediately. This is not hypothetical: it once produced a green `cbt` for a change that broke 13 of 25 spec suites, and the breakage survived two code reviews because both trusted the green suite. Run `npx jest --clearCache` before verifying any change to dependencies, `tsconfig.json`, or a `.d.ts` boundary.

Coverage is gated, not merely measured: `jest.config.ts` carries a global `coverageThreshold`, both workflows run `npm test -- --coverage`, and `cbt` runs `test:coverage` so the threshold binds locally too — it used to bind only in CI, which made "the only gate" a claim `cbt` could not back. Raise the numbers when coverage rises; never lower them to make a build pass.

**TypeScript is pinned below 7, on purpose.** `ts-jest` — which compiles every spec — declares `peerDependencies.typescript: ">=4.3 <7"` (checked across its six most recent releases; its `next` dist-tag is an *older* prerelease than `latest`, not a forward path). `typescript-eslint` is tighter still, capping at `<6.1.0`. Before retrying this upgrade, check both packages' current peer range with `npm view <pkg> peerDependencies`; do not force the install with `--legacy-peer-deps`, `--force`, or an `overrides` entry to get past a real peer conflict — that trades a known state (outdated TypeScript) for an unverified one (a compiler nothing in the toolchain has agreed to support). See `CHANGELOG.md` under `## \`v6.0.0\`` for the full record.

## Architecture invariants

These are the things that bite. Everything else is readable from the source.

**The eventized marker.** `asEventized(obj)` attaches a non-enumerable property keyed by `NAMESPACE` (`Symbol.for('eventize')`) holding `{store, keeper}`. That hidden slot _is_ the definition of an emitter — `isEventized()` just probes for it. This is why eventize works on plain `{}`, existing objects, and class instances interchangeably, and why nothing may ever enumerate its way onto the public surface.

In the **types** the slot is opaque (since v6.0.0): `EventizedObject` declares it as a branded empty shape, and the real `{keeper, store}` lives in `src/internals.ts`, which `src/index.ts` does not re-export. Declaring the pair inline made `EventKeeper`, `EventStore` and — through the store — `EventListener` reachable from an exported type, so tsup inlined all three into `lib/index.d.ts`. Everything internal reads them through `internalsOf()`, which holds **the one cast** this boundary costs. If a second cast is ever needed to make it work, the boundary is in the wrong place and belongs redrawn, not patched. `grep -c '^declare class' lib/index.d.ts` must stay at 1 (`Eventize`); anything higher means an internal class found its way back onto the published surface.

**Two collaborators per emitter.** `EventStore` is the listener registry (binary-search insertion by priority, removal via `(listener?, listenerObject?, forceRemove?)`). `EventKeeper` is the retained-events log. Their interplay has one ordering rule worth protecting: `subscribeTo` collects retained events into a local `retainedEvents[]` and `EventKeeper.publish()` flushes them **after** registration completes, so a new subscriber sees replayed values in emission order rather than mid-registration.

**`EventStore` clone-on-mutate — the held-count protocol, and the rules a new mutation path must obey.** Since v6.0.0 `forEach()` walks the **live** buckets; it does not copy them. What protects the walk from a listener that subscribes or unsubscribes inside its own callback moved to the mutating side. A bucket is not a bare array: `ListenerBucket` carries a count of the walks currently stepping through it, under a module-private symbol, `forEach()` counts itself in and out again in a `finally`, and `bucketForMutation()` clones a bucket if and only if that count is non-zero, swapping the clone into `namedListeners` — or into the `catchEmAllBucket` field behind the read-only `catchEmAllListeners` getter — while the walk keeps the array it started on.

The question is not "is a walk running", it is "is a running walk holding *this* array". Those are wildly different questions in practice: a `forEach()` holds **at most two** arrays, the named bucket for its event and the wildcard bucket, and every other bucket in the store may be changed in place at any time, dispatch or no dispatch. Held-ness is a property of the array, so it is stored on the array — one integer field, one load to read it, no state in the store and nothing to reset. The intermediate design kept a stack of held slots in the store and scanned it; that is correct but scales with nesting depth, and it scales on the wrong case: a mutation of a bucket nobody holds finds no match and therefore always walks the whole chain. Measured over forwarding cascades of depth 2 to 512 that mutate at every level, that design ran between 1.21× and 1.98× HEAD, rising with depth; the count on the bucket runs between **1.04× and 1.16×, with no trend over depth at all**. Take the range, not a cell: individual cells move by ten points between runs, and a point figure quoted from one of them is a fortnight away from being wrong.

Consequences, all load-bearing:

- **Every array that can become a bucket is born in `createBucket()`.** The held count is assigned immediately after the array exists and before any element goes in, so all buckets share one hidden class and the field load stays monomorphic. This is why the clone in `bucketForMutation()` goes through `createBucket(bucket)` rather than a bare `slice(0)`: `slice` copies elements and nothing else, so a hand-rolled clone arrives without the property, in a different shape, reads as *held* (`undefined === 0` is false), and buys itself one copy it does not owe — which then installs a well-formed clone and hides the mistake for good. Anything that puts a fresh array into `namedListeners` or `catchEmAllBucket` has to come from `createBucket()`.
- **A bucket is not a bare array.** `ListenerBucket` carries the held count under a module-private symbol, so `Object.keys()`, `for…in`, an object spread and `JSON.stringify` never see it — but `Reflect.ownKeys()` does, and so does Jest, whose `toEqual` and `toStrictEqual` compare own enumerable symbols. A bucket therefore never equals a plain array literal. **Compare buckets by identity and length**, which is what `src/EventStore.spec.ts` and `src/emit-reentrancy.spec.ts` do throughout; both reach into `store.namedListeners.get()` directly and are the two files this bites.
- **A clone costs once per bucket and walk — and nothing at all for a bucket no walk is holding.** Both halves matter. A bare "a dispatch is running" flag makes `n` mutations in one dispatch cost `n` clones and `n(n+1)/2` copied slots, which is worse than the unconditional copy it replaced; a burst of `once()` listeners releasing themselves is the ordinary way to hit that, not a corner case. Tracking *installed* arrays instead of *held* ones fixes that half and breaks the other: a teardown listener calling `off(ε, componentInstance)` across `k` event names then pays `k` clones where the copy-before-walk version paid one. Four specs measure the count by holding bucket identity across successive mutations — `clones a bucket once per walk, not once per mutation`, `does not clone a bucket no walk is holding` and `does not clone anything when a dispatch only subscribes to other events` in `src/EventStore.spec.ts`, plus the `once()` burst case in `src/emit-reentrancy.spec.ts`.
- **It is a count, not a flag.** Nested emits over the same bucket each add one and each take their own back; a boolean would let the inner walk's exit tell the store the outer one is over. `still clones after a nested walk over the same bucket has returned` is the witness, and it has to be that one: the two walks in it step through the *same* array. `clones an enclosing walk’s bucket when a nested walk mutates it` reads like the same case and is not — its walks hold two different buckets, so a per-bucket boolean keeps it green. A walk also counts *both* of its buckets: tracking only the named one splices the wildcard array under a merge dispatch, which `replaces both buckets when everything is removed mid-dispatch` pins.
- **An empty bucket is never counted, because it is never walked.** `forEach()` skips a bucket of length 0 entirely, so a wildcard subscription taken during a named dispatch goes in place and costs nothing. The dispatch still does not see it — the walk never looks at that array again.
- **Every path that changes a bucket's *contents* must route through `bucketForMutation()`.** One that splices a live array directly makes a mid-dispatch subscription visible to the running emit again, and no existing spec would notice — the bucket-identity cases are the only place the mechanism is observable at all, because everything else in the suite asserts dispatch outcomes that hold either way.
- **The truncation exception.** Two paths change a bucket without routing through it, and both are deliberate: `removeByEventName()` and `removeAllListeners()` do not *change* a bucket, they let go of it — the map entry is deleted or the whole map cleared. The `bucket.length = 0` they perform on top is a courtesy to a caller still holding the array from `getListenersForEventName()`, and it is the one thing a walk stepping through that very array must not suffer, so both skip it exactly then, on the bucket's own held count. A caller that fetched the bucket before such a dispatch is therefore left holding a full array of detached listeners instead of an empty one; that is unreachable through the public API and recorded in `CHANGELOG.md`. The guard in `removeByEventName()` is not cosmetic and not redundant with its sibling: `survives off(ε, name) for the very name being dispatched, alongside a wildcard listener` in `src/emit-reentrancy.spec.ts` is the only case that takes it, and without the guard that spec does not merely fail — `emit()` throws the internal hole-guard `Error` at the caller, because `mergeWalk()` read the named bucket's length before the truncation took it away. Cloning a bucket in order to truncate the clone and then drop it would be theatre. Don't "fix" these two into the routed path.
- **Call `bucketForMutation()` only when a mutation is certain, never speculatively.** A dedup in `add()` and a removal that matches nothing leave bucket identity alone on purpose; the moment a no-op replaces the array, "identity changed" stops meaning "the registry changed" and those specs stop measuring anything. That is why the removal loops call it at the first match and not before, reading their candidates from the array they were handed and splicing into whatever comes back — the clone is element-for-element below every index spliced so far, so one backward pass addresses both arrays with the same index and needs neither a collect phase nor an allocation.
- **The count is given back from a `finally`.** A listener that throws must not leave a dead walk counted in, or every later mutation of that bucket clones for the rest of its life. `mutates in place again after a listener threw mid-dispatch` in `src/EventStore.spec.ts` is the witness — `src/emit-throwing-listener.spec.ts` is not, and stays green with the decrement neutralised.
- **The clone's destination is derived from the array, not from the event name.** `bucketForMutation()` decides between the wildcard slot and `namedListeners` by comparing the bucket against `catchEmAllBucket`. Deriving it from the name instead would send the clone of a `'*'` key in `namedListeners` — which the public `getListenersForEventName('*')` creates on demand — into the wildcard slot. That damage cannot actually happen, and the rule is worth keeping anyway: `forEach()` never walks a `'*'` key, so such a bucket is never counted, never cloned, and the branch is unreachable rather than merely untested. No spec can catch the swap; keeping the derivation on the array is what keeps the question closed instead of resting on an argument two files away.
- **The merge branch reads `iLen`/`jLen` once, before the loop, and holds two array references across it.** Both are safe only because of the rules above: a mutation from inside `fn` clones what it changes, so neither array can grow, shrink or acquire a hole mid-walk. The hole guard stays anyway — a hole means a corrupted array, not a value to dispatch around.
- **The merge loop lives in `mergeWalk()`, outside `forEach()`, and inlining it back is a measurable regression.** `forEach()` carries a `try`/`finally`, which puts it near TurboFan's inlining budget, so its bytecode size decides whether its own callers inline it. With the merge loop in the body the effect was bimodal and stable: two benchmark harnesses differing only in trivia measured the same mutation-free 64-listener dispatch at 535 ns and 653 ns, one value each, reproducibly. Moving the loop out took both to ~535. Keep `forEach()` small — anything added to it is paid on every dispatch, including the ones that never reach the new code.
- **`getListenersForEventName()` creates buckets lazily and hands out live references.** A reference held across a mutation may be the pre-clone array. Every caller inside the store uses it immediately; the spec helpers copy it on the spot. Keep it that way.

**Three API surfaces, one implementation** (`eventize-api.ts` → `eventize.ts`). Standalone functions, `eventize.inject(obj)` methods, and `class Eventize` all delegate to the same `on`/`emit`/`off`. Never fork logic into a surface. The class/inject side casts to loose implementation-shape signatures on purpose — the public overload sets are tuned for end users and don't accept a spread of `SubscribeArgs`.

**Two dispatch paths in `emit`.** `_emit` handles eventized targets; `_duckEmit` handles non-eventized ones (v5+: `obj[eventName](...args)`, then `obj.emit(eventName, ...args)`, then no-op). Three things must hold on both sides, or `emitAsync` aggregation silently diverges between them: both must reject `'*'`, both must funnel return values through the same `returnValue` callback, and both must resolve the event-named member through `dispatchableMember()` (`utils.ts`) rather than reading `target[eventName]` raw — that is the `Object.prototype` boundary, and a path that skips it answers `emit(ε, 'toString')` while the other one doesn't. `emitAsync` differs from `emit` only in that aggregation — invocation is always synchronous.

**`subscribeTo` and `types.ts` move in lockstep.** `_subscribeTo` decodes the overloaded `on()` shapes positionally (event name(s), optional priority, listener function or method-name + listener object, or a bare listener object). Changing the API means changing `SubscribeArgs` _and_ the parsing; the spec files exercise the corner cases. What may enter the store is decided by `detectListenerType()` (exported from `EventListener.ts`, and the same tag `EventStore.isSimilar()` compares) plus a falsy test in front of it — a new listener shape has to be added there, not at the call site, or it will be rejected before it reaches a listener instance. The priority is checked with `Number.isNaN`, never with `Number.isFinite`: `Priority.Max` / `Priority.Min` are `±Infinity`.

**Counters are per module instance.** `EventListener.lastId` (secondary sort
among equal priorities) and `EventKeeper.nextOrderId` (replay order of
retained events) are module-global `let` variables. Loading the ESM and the
CJS build in the same process — which the dual-format package permits —
gives you two independent counter pairs, so ordering stability is guaranteed
per loaded module instance, not per realm. This is deliberate: the
`Symbol.for('eventize')` marker is realm-wide because identity must be, the
counters are not because sorting only ever compares listeners on the same
emitter, and one emitter comes from one module instance.

## Known asymmetries

Verified quirks that look like bugs but are load-bearing or simply undocumented. Don't "fix" them without a CHANGELOG entry.

- `off(ε, name)` doesn't merely clear the retained *value* for that event — `keeper.remove()` drops the retain *policy* too, so it behaves like `unretain()`. Later emits of that event are no longer retained until `retain()` is called again.
- The array branch of `off()` is reached from two directions: an explicit `off(ε, [name, …])` and the unsubscribe function of a multi-event `on()`, which passes an array of `EventListener` instances. Anything filtering that array must keep event names and ignore listener instances — `isEventName` does, a `typeof === 'string'` test silently dropped symbol names (fixed). An array containing `'*'`, `null` or `undefined` never reaches this branch: `isBulkRemoval()` sends it to the bulk path first, which is why the unsubscribe-handle direction still needs the filter — listener instances make `isBulkRemoval()` false. That predicate mirrors `EventStore.remove()`'s *effective* array behaviour, not its condition: the store forwards each element back into itself with a null listener object, so one nullish element lands in the wipe-everything branch. Anything else that decides "is this argument bulk?" has to reproduce that, not just test for `'*'`.
- Reference-counted dedup is an `on()` property, not a store-wide one. `EventStore.add()` takes a `noDedup` flag and `once()` passes `true`, so every `once()` gets its own `EventListener`: two one-shot subscriptions mean two firings, two replays of a retained value, and two independently releasable handles. Folding them (pre-v6.0.0) left the second `callAfterApply` overwriting the first, so one emit decremented `refCount` from 2 to 1 and the surviving handle's own idempotence guard could never take it to 0 — a `once()` that fired forever.
- `emitAsync()` resolves to `undefined`, not `[]`, when no listener returned a non-null value.
- `emit()` on a non-eventized target no longer throws (v5). Typo safety now comes from typed emitters or an explicit `isEventized()` guard.
- No recursion guard. `A → B → A` forwarding and same-event re-emission overflow the stack by design — the v4.2 guard forbade legitimate patterns and was reverted.
- `off(ε, undefined)` is not a no-op — it takes the same branch as `off(ε)` and removes **every** listener plus, since v6.0.0, **all** retained state. Cleanup code that forwards a possibly-missing value through (`off(ε, handlers[name])`) wipes the emitter when the lookup misses, rather than doing nothing. Guard the call, or keep the `on()` handle and call that.
- The unsubscribe handles from `on()` and `once()` are single-shot: `makeUnsubscribe()` nulls its captured emitter before calling `off()`, so a second call is inert. Not cosmetic — `on()`'s reference-counted dedup means two handles can share one `EventListener`, and without the guard one handle called twice decremented the count twice and released the other handle's registration. The nulled capture doubles as the consumed flag on purpose: a separate boolean would leave the emitter in the closure of every kept handle, which is precisely the leak MEM-001 described. Both captures — emitter and listeners — live in **one** slot and are nulled together, so a single null test releases both and narrows both. Two separate `let`s would buy a branch that can never be taken. Clearing the listeners is only worth anything because the handle no longer carries `.listener` / `.listeners` in public — while it did, the same instances hung off it either way and clearing the closure copy released nothing. Reducing the handle to `() => void` is what made the closure the only holder; the two belong together.
- **"A consumed handle holds nothing" is true since v6.0.0 — an *unconsumed* one is the case to worry about.** Up to v5.1.0 the qualifier was real: a call that merely decremented a shared reference count left the listener registered and populated, and the handle went on holding it, so the emitter stayed reachable through the listener. Two shapes did it, both `WeakRef`-verified and still pinned in `src/lifecycle.spec.ts`: an `on()` that deduped onto a `once()` whose event never fired — the surviving listener's `callAfterApply` is the `once()` handle's closure — and the emitter subscribed as its own listener object twice, in any of the three dedup-eligible spellings `on(ε, 'foo', ε)`, `on(ε, 'foo', 'method', ε)` and the wildcard `on(ε, ε)`. The back-reference sits in a different slot of the surviving `EventListener` per spelling (`listener` for the object form, `listenerObject` for the method-name form), so a check watching one field misses the other. Clearing the listener capture cut the chain at the handle, and the pins now assert `collected` where they used to assert `still reachable`. **What survives, and what the control group in that file exists for: a handle that was never called still pins the emitter by design.** In the `once()`-shape above, that unconsumed `once()` handle is exactly what keeps the emitter alive. **MEM-002 itself is untouched** — `findSimilarListener()` still deduplicates onto a listener carrying a `callAfterApply`, so one reference count still spans two lifetimes; only its memory consequence is gone. Refusing that dedup is still a behavior change nobody has costed; don't take it without a CHANGELOG entry. That refusal — `findSimilarListener()` declining to dedup onto a listener that already carries a `callAfterApply` — is deferred past v6.0.0 to the next major on purpose: its blast radius on consumers that built on the current shared-refcount behavior is unmeasured, so it does not ship as a silent fix.
- `EventListener` is not exported at all, in any namespace, and that is now true of the emit as well. Up to v5.1.0 `src/index.ts` re-exported it as `export type`, but tsup's dts rollup inlined the class — it was reachable from `UnsubscribeFunc` — and dropped the type modifier, so `lib/index.d.ts` declared and *exported* it in the value namespace while the runtime bundles exported nothing under that name: `import {EventListener}` from the ESM build threw a `SyntaxError`. Reducing `UnsubscribeFunc` to `() => void` and dropping the re-export together took the name out of the emitted export list. The class is still `declare class EventListener` inside `lib/index.d.ts`, because `EventStore` references it and `EventizedObject` exposes the store — inlined but unexported, which is what it should always have been. `attw --pack` passes in all four modes. Re-adding a `export type {EventListener}` puts the whole problem back.
- `retain(ε, [name, …])` rejects a wildcard atomically: nothing is retained if `'*'` appears anywhere in the array. `emit(ε, [name, …])` does not — it dispatches the names preceding `'*'` and then throws. Both are pinned by specs; unify them only with a CHANGELOG entry. `on(ε, [name | [name, priority], …])` sides with `retain()`: `_subscribeTo()` resolves every per-event priority into one list and validates it before the first `register()` call, so a `NaN` in the last tuple leaves nothing subscribed.
- `retain()`, `unretain()` and `retainClear()` treat `'*'` specially, but not identically: `retain(ε, '*')` throws — `'*'` stays subscribe-only, matching `emit()`. `unretain(ε, '*')` and `retainClear(ε, '*')` instead mean "all retained events": the former drops every retain policy and every retained value, the latter drops only the values and keeps the policies.
- The `Object.prototype` boundary covers two of the three member lookups, on purpose. `dispatchableMember()` (in `utils.ts`) skips a member identical to `Object.prototype`'s same-named one, and both the listener-object branch of `EventListener.apply()` and `_duckEmitOne()` route through it — they have to agree, or `emitAsync` aggregates differently for eventized and non-eventized targets. The method-name branch (`listenerObject[listener]`) does **not**: `on(ε, 'evt', 'toString', obj)` spells the method out, so the inherited hit is the caller's choice. A spec in `EventListener.spec.ts` pins that asymmetry in both directions; don't "unify" it without a CHANGELOG entry.
- `off(ε, eventName, listenerObject)` unretains the *whole* event name — drops its retained value and policy — even though it only detaches one listener object's subscription and leaves any sibling listener for that same name subscribed. Unlike the bulk forms — which v6.0.0 made clear retained state too — this one is not scheduled to change: `git log -L` shows the branch unchanged since the 4.0.0 functional API, and fixing it now would be breaking. See `docs/lifecycle.md`. The array sibling, `off(ε, [eventName, …], listenerObject)`, is not the same case: `EventStore.remove()`'s array branch requires `listenerObject == null`, so with one given the store never detaches anything — it falls through to a listener-identity lookup an array can never match. Since v6.0.0 (COR-001) the keeper mirrors that same condition, so this form is a complete no-op on both halves rather than a name-only unretain. Don't fold the two together; the named form still detaches a listener via `forceRemove`, the array form never did.
- `off(ε, '*', listenerObject)` is a *targeted* removal, not a bulk one, and `EventStore.removeByEventNameAndListenerObject()` has to special-case the wildcard to make it one: `'*'` is not a key in `namedListeners`, so the branch searched a bucket wildcard listeners can never be in and removed nothing (fixed in v6.0.0). Two boundaries hold it in place, both pinned in `off.spec.ts`: a **named** subscription of the same object survives — `off(ε, listenerObject)` is the form that takes both — and retained state is untouched, which needs no code of its own because `retain()` rejects `'*'`, so the `keeper.remove('*')` that `off()` performs finds nothing. Reference counting behaves as in the named case: the association-matching removal path detaches outright without consulting `refCount`, so one call releases a `refCount`-2 registration.
- The "equal priorities keep insertion order" guarantee holds only within a bucket. `sortByPriorityAndId` breaks a priority tie on ascending `id`, but that function only ever runs inside `findInsertIndex` against listeners of the same kind (named-for-one-event, or wildcard). The merge in `EventStore.forEach()` that interleaves a named bucket with `catchEmAllListeners` compares `cur.priority >= other.priority` and never looks at `id`, so at equal priority the named listener always goes first — independent of registration order. This is a documented, deliberate scope limit, not a bug: `forEach()` is not to be changed to consult `id` across the bucket boundary. Both registration directions are pinned by name in `src/EventStore.spec.ts` — the wildcard-first direction was already exercised, just implicitly, inside the older mixed-priority fixture there (a wildcard registered before a same-priority named listener, with the named one expected first); the named-first case is new. Neither test closes a coverage gap; they give an existing pin its own name and put the reverse direction next to it.

## Conventions

- Specs live next to sources as `*.spec.ts`; Jest `testMatch` is restricted to `src/**`.
- Every feature or bugfix gets a spec.
- Relative imports carry no extension — `tsup` writes the output extensions.
- `lib/` is generated and git-ignored. Never edit it, never read it to answer a question about behavior.
